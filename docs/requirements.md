# Calorie Lens 需求文档

## 1. 项目概述

Calorie Lens 是一款基于手机拍照的食物卡路里估算 App。用户可以拍摄或上传一张餐盘照片，系统通过视觉模型识别盘中食物，并结合拳头参照物估算食物份量、重量和卡路里。识别结果以图片标注和列表形式展示，用户可以手动调整食物种类、克重、热量密度和标注位置。

本产品定位为“快速饮食记录工具”，目标不是替代专业营养师或医疗设备，而是帮助用户以较低操作成本完成日常饮食热量记录。

### 1.1 版本说明

项目目前同时维护两个实现，产品功能一致：

- **原版**（仓库根目录）：原生 HTML/CSS/JS + Node `http` 服务，前端发布到 GitHub Pages。
- **Next.js 版**（`nextjs/` 目录）：React 前端 + Next.js API 路由，面向 Vercel 等云平台部署，存储可接 Redis。

除特别标注“Next.js 版”的条目外，本文档中的需求对两个版本同样适用。

## 2. 目标用户

- 健身、减脂、增肌人群：希望快速记录每餐热量和大致营养摄入。
- 慢病管理用户：需要粗略追踪每日饮食，但不想手动称重。
- 普通健康管理用户：想知道一餐大概多少卡路里。
- 营养师或教练：可作为客户饮食记录的辅助工具。

## 3. 用户痛点

- 手动搜索食物、输入克重流程太慢。
- 普通用户难以判断一份食物有多少克。
- 一盘饭菜常由多种食物组成，传统记录 App 很难快速拆分。
- 拍照识别不一定准确，需要用户能快速修正。
- 高清照片直接上传会增加 API 成本和处理时间。

## 4. 产品目标

- 用户能在 30 秒内完成一次餐食热量初步记录。
- 系统能识别盘中多个食物，并分别给出估算重量和卡路里。
- 当食物大小不确定时，用户可用拳头作为体积参照物。
- 用户可对所有识别结果进行手动校正。
- 控制 API 成本：同一用户 24 小时内限制分析次数，并在上传前压缩图片。

## 5. 核心用户流程

### 5.1 拍照分析流程

1. 用户打开 App。
2. 点击“打开相机”。
3. 将食物放入主取景区域。
4. 如需份量参照，将拳头放入右下角参照区域。
5. 点击“拍照”。
6. App 清除上一张图片的识别结果，并压缩新图片。
7. 用户点击“分析照片”。
8. 服务端检查用户 24 小时分析次数。
9. 服务端调用 Gemini 2.5 Flash 识别图片。
10. 服务端用 USDA FoodData Central 校准每项食物的 `kcal/100g`。
11. App 展示每项食物的名称、重量、卡路里、营养数据来源和图片标注。
12. 用户手动调整不准确的项目。
13. 用户点击“保存记录”。

### 5.2 上传照片流程

1. 用户点击“上传照片”。
2. 系统打开相册或文件选择器。
3. 用户选择照片。
4. App 清除上一张图片的识别结果。
5. App 将图片最长边压缩到 1280px，并以 JPEG 质量 0.82 保存。
6. 用户点击“分析照片”。
7. 后续流程同拍照分析。

### 5.3 手动校正流程

1. 用户查看识别结果。
2. 如食物名称错误，可在食物名称输入框中修改。
3. 如重量不准确，可修改克重。
4. 如热量密度不准确，可修改 `kcal/100g`。
5. 如图片标注位置不准确，可拖动标注卡片。
6. 总重量和总卡路里实时重新计算。

## 6. 功能需求

### 6.1 拍照与上传

- App 应支持调用手机摄像头拍照。
- App 应支持从相册或本地文件上传图片。
- “上传照片”不得强制打开相机。
- 用户选择或拍摄新图片后，应自动清除上一张图片的识别标注和食物列表。
- 图片预览应显示在取景框中。
- 拍照完成后应关闭摄像头，释放相机占用。（Next.js 版已实现，原版拍照后摄像头仍保持开启）
- 用户再次选择同一张图片时也应重新加载。（Next.js 版已实现）

### 6.2 取景辅助

- 取景框应显示食物主区域。
- 取景框应显示拳头参照区域。
- 参照区域用于引导用户把拳头放在食物旁边，辅助估算体积。
- 用户可通过滑块设置拳头体积，默认值为 350 ml。
- 拳头体积变化后，当前食物重量估算应按比例调整。

### 6.3 图片压缩

- 上传或拍照后，前端应在本地压缩图片。
- 图片最长边应限制为 1280px。
- 压缩格式应为 JPEG。
- JPEG 质量默认值为 0.82。
- 服务端应限制请求体大小，避免高清原图直接进入模型。

### 6.4 AI 图片分析

- 服务端默认使用 Gemini 2.5 Flash。
- API Key 应只保存在服务端 `.env` 文件，不得暴露给前端。
- 服务端应支持通过 `AI_PROVIDER` 切换视觉模型提供方。
- 当前支持：
  - `gemini`
  - `openai`
- 当未配置 API Key 或模型调用失败时，前端应提示错误，并回退到本地模拟结果。
- AI 返回结果应包含：
  - 食物名称
  - 估计克重
  - 每 100g 卡路里
  - 置信度
  - 图片标注位置
  - 备注说明
  - 用于 USDA 搜索的英文标准名 `usdaQuery`（包含生熟状态和烹饪方式）

### 6.4.1 营养数据校准

- 配置 `USDA_API_KEY` 后，服务端应使用 `usdaQuery` 搜索 USDA FoodData Central，用数据库中的 `kcal/100g` 替换模型估算值。
- 应优先匹配 Foundation、SR Legacy、Survey (FNDDS) 数据，不使用品牌食品数据。
- USDA 无匹配或请求失败时，应保留模型估算值，不得让整次分析失败。
- USDA 查询结果应持久缓存，默认 30 天（`USDA_CACHE_TTL_DAYS`）；缓存过期后刷新失败时，继续使用旧缓存。
- 每个食物项应显示营养数据来源：USDA（含匹配到的条目名称）、模型估算、本地参考值或手动调整。
- 用户修改食物名称后，来源应提示“名称已修改，热量值待确认”。

### 6.5 分析次数限制

- 同一个本机用户 24 小时内最多调用 3 次图片分析（`DAILY_ANALYSIS_LIMIT`）。
- 前端应为本机用户生成 `clientId` 并保存在 `localStorage`。
- 服务端应根据 `clientId` 记录调用次数，并持久保存用量记录：
  - 原版：保存在本地文件 `.analysis-usage.json`。
  - Next.js 版：配置 Upstash Redis 时保存在 Redis；未配置时保存在 `nextjs/.data/usage.json`。
- 用量记录文件不应上传到 GitHub。
- 只有分析成功才计入次数。
- 超过限制时，应返回明确错误信息。

### 6.6 识别结果展示

- App 应展示总热量。
- App 应展示总重量。
- App 应展示整体置信度。
- 每个食物应单独显示为列表项。
- 每个食物应在图片上显示标注。
- 标注应包含食物名称、克重和卡路里。
- 标注应支持拖动调整位置。

### 6.7 手动编辑

- 用户应能修改食物名称。
- 用户应能修改估计重量。
- 用户应能修改 `kcal/100g`。
- 用户应能删除食物项。
- 用户应能手动添加食物项。
- 编辑后总热量和总重量应立即更新。

### 6.8 历史记录

- 用户应能保存当前餐食记录。
- 历史记录应展示：
  - 总卡路里
  - 总重量
  - 食物项数量
  - 保存时间
- 用户应能清空历史记录。
- 当前版本历史记录保存在浏览器 `localStorage`。

## 7. 非功能需求

### 7.1 性能

- 图片压缩应在前端完成，减少上传体积和 API 成本。
- 单次图片分析应尽量在 10 秒内返回。
- 前端交互应在手机浏览器中保持流畅。

### 7.2 安全

- API Key 不得写入前端代码。
- `.env`、`.env.local`、`.analysis-usage.json`、`.nutrition-cache.json`、`nextjs/.data/` 必须加入 `.gitignore`。
- 服务端应限制请求体大小。
- 当前原型不应收集用户真实身份信息。

### 7.3 可用性

- 当相机不可用时，应提示用户改用上传照片。
- 当图片识别失败时，应提供可编辑的模拟结果，避免流程中断。
- 所有 AI 结果应被视为估算值，允许用户修正。

### 7.4 兼容性

- 应支持现代手机浏览器。
- 应支持桌面浏览器上传图片测试。
- 摄像头功能依赖浏览器权限和 HTTPS/localhost 环境。

## 8. 数据结构

### 8.1 食物项

```json
{
  "id": "string",
  "name": "米饭",
  "usdaQuery": "cooked white rice",
  "grams": 180,
  "kcalPer100g": 96,
  "confidence": 0.72,
  "notes": "基于拳头参照估算",
  "nutritionSource": "usda",
  "nutritionDataType": "Survey (FNDDS)",
  "matchedFood": "Rice, white, cooked, glutinous",
  "fdcId": 2708422,
  "position": {
    "left": 18,
    "top": 28
  }
}
```

`nutritionSource` 取值：

- `usda`：已用 USDA 数据校准。
- `gemini`：模型估算（USDA 未配置、无匹配或请求失败）。
- `local`：本地模拟结果。
- `manual`：用户手动修改了 `kcal/100g` 或手动添加。
- `renamed`：用户修改了名称，热量值待确认（仅 Next.js 版）。

### 8.2 分析响应

```json
{
  "foods": [],
  "overallConfidence": 0.65,
  "usedFistReference": true,
  "message": "识别完成，请检查重量是否准确。",
  "provider": "gemini",
  "model": "gemini-2.5-flash",
  "nutritionDatabase": "USDA FoodData Central",
  "remaining": 2
}
```

超过次数限制时返回 `429`：

```json
{
  "allowed": false,
  "status": 429,
  "error": "同一个用户 24 小时内最多只能分析 3 张图片。",
  "remaining": 0,
  "resetAt": "2026-10-03T08:00:00.000Z"
}
```

### 8.3 历史记录

```json
{
  "id": "string",
  "time": "07/24 18:30",
  "totalCalories": 650,
  "totalGrams": 520,
  "foods": [
    {
      "name": "米饭",
      "grams": 180,
      "kcalPer100g": 116
    }
  ]
}
```

## 9. 配置需求

原版使用根目录 `.env`，Next.js 版使用 `nextjs/.env.local`。示例：

```text
AI_PROVIDER=gemini
GEMINI_API_KEY=your-gemini-api-key-here
GEMINI_MODEL=gemini-2.5-flash
USDA_API_KEY=your-usda-api-key
USDA_CACHE_TTL_DAYS=30
DAILY_ANALYSIS_LIMIT=3
OPENAI_API_KEY=sk-your-openai-api-key-here
OPENAI_MODEL=gpt-4.1-mini
PORT=4173
```

Next.js 版额外支持（线上部署时使用）：

```text
UPSTASH_REDIS_REST_URL=
UPSTASH_REDIS_REST_TOKEN=
```

也兼容 Vercel 注入的 `KV_REST_API_URL` / `KV_REST_API_TOKEN`。Next.js 版端口由 `npm run dev` 固定为 4174，不读取 `PORT`。

API Key 获取地址：

```text
Gemini: https://aistudio.google.com/app/apikey
USDA:   https://fdc.nal.usda.gov/api-key-signup/
```

## 10. 边界情况

- 图片中没有食物：返回空食物列表，并提示无法检测到食物。
- 图片过大：前端压缩，服务端仍应拒绝超大请求。
- 用户超过每日限制：返回 429，并提示 24 小时内最多 3 次。
- API Key 无效：返回明确错误，不应暴露完整密钥。
- 模型返回非 JSON：服务端应返回识别失败，前端回退到模拟结果。
- 用户重新拍照或上传：旧标注必须清空。

## 11. 当前版本限制

- 体积和重量估算仍依赖视觉模型推断，不能保证精确。
- 已接入 USDA FoodData Central；数据库数值更可靠，但视觉识别与数据库条目匹配仍可能存在偏差。当前匹配只按关键词命中数打分，会出现明显错配，例如 “steamed broccoli florets” 匹配到 “Oysters, steamed”。
- 每日限制基于本机 `clientId`，不是账号级别，清除浏览器数据会重置。
- 原版用量记录存储在本地文件，不适合多服务器部署；Next.js 版配置 Redis 后可解决。
- 原版发布在 GitHub Pages 上时没有后端，线上只能使用模拟结果；需要真实识别时应使用 Next.js 版部署。
- 历史记录只保存在浏览器本地，换设备后不可同步。
- 当前没有用户登录、云端数据库和支付系统。

## 12. 后续迭代建议

- 扩展中国食物成分表或自建中餐营养数据库，提高中式混合菜匹配率。
- 增加用户账号和云端历史同步。
- 增加营养素拆分：蛋白质、脂肪、碳水。
- 增加餐别分类：早餐、午餐、晚餐、加餐。
- 增加一键确认和批量编辑。
- 增加食物识别反馈机制，用于改进提示词和数据库映射。
- 增加更可靠的参照物选项，如银行卡、勺子、标准餐盘。
- 增加会员或付费策略，与每日分析次数限制联动。
- ~~上线时将本地限额替换为数据库或 Redis 限额。~~ Next.js 版已支持 Redis 限额。
- 改进 USDA 匹配打分，减少错配（如加入食物类别校验、同义词表）。
- 增加账号后，可接入 Supabase（Auth + Postgres）统一承担登录、云端历史和限额存储。

## 13. 验收标准

- 用户能打开 App 并看到拍照界面。
- 用户能打开相机并拍照。
- 用户能从相册上传照片。
- 上传新照片后，上一张照片的标注会清空。
- 上传高清照片后，前端会压缩图片再分析。
- 配置 Gemini API Key 后，系统能返回真实识别结果。
- 配置 USDA API Key 后，食物项显示 USDA 来源和匹配条目。
- 同一用户 24 小时内第 4 次分析应被拒绝。
- 用户能编辑食物名称、重量、热量密度。
- 用户能拖动图片上的食物标注。
- 用户能保存记录并在历史区看到结果。
